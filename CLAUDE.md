# CLAUDE.md

TextSkill, набор правил и скиллов, которые заставляют тексты на русском звучать по-человечески, а не как генерация AI. Это не код: ядро правил плюс автозапускаемые скиллы Claude Code.

## Единый источник правды

- **`postroenie.md`**, единственный источник про то, как строится текст до черновика: порядок работы (читатель, материал, ситуация, проверка), что входит в текст, порядок в тексте, предложение, разметка, числа, хук авторского голоса. Новое правило о том, как писать, идёт сюда.
- **`writing-rules.md`**, словарь проверки и единственный источник паттернов: запрещённая лексика, синтаксис, структура, типографика, ритм. Читается после черновика и при аудите. Новый паттерн машинности идёт сюда.
- **`mosty.md`**, единственный источник про связь между утверждениями: типы связи (цепная/параллельная/присоединительная), порядок тема→рема, обоснование причинности, разновидности ложного моста. Дополняет ядро, не дублирует и не входит в него физически, чтобы не раздувать один файл. Новое правило про то, как одно утверждение вытекает из другого (а не про лексику или ритм одного предложения), идёт сюда, не в `writing-rules.md`.
- **`audit.md`**, только методика аудита (карта категорий, шкала, формат отчёта). **Не дублируй сюда стоп-листы.** Паттерны он берёт из ядра. Если переписываешь промт для обычного чата, ссылайся на ядро, а не копируй его.
- Форматные правила (структура поста, статьи, README) живут в соответствующем `.claude/skills/*/SKILL.md`, не в ядре.

## Маршрутизация скиллов

Скиллы срабатывают автоматически по описанию во фронтматтере. Логика выбора:

- «напиши пост / для тг / итоги недели / ответь на комментарий на хабре» → **write-post** (пост в канал или тред, дайджест, публичный ответ на комментарий; граница с write-article по формату площадки, не по длине).
- «напиши статью / лонгрид / эссе» → **write-article** (от нескольких сотен слов).
- «напиши / обнови readme» → **write-readme**.
- «напиши документацию / опиши метод / API / справочную страницу» → **write-docs**.
- «напиши лендинг / посадочную / продающую страницу» → **write-landing**.
- «напиши КП / коммерческое предложение» → **write-kp**.
- «напиши письмо / холодное письмо / рассылку» → **write-email**.
- «ответь коллеге / напиши в задачу / подготовь ответ / подправь мой ответ», а также любой текст, который агент сам предлагает отправить человеку → **write-message** (рабочее сообщение: строится по карточкам ситуаций, проверка по `check.md` и `scripts/lint_text.py` идёт отдельным шагом после черновика).
- «напиши вакансию / job description» → **write-vacancy**.
- «напиши пресс-релиз / релиз для СМИ» → **write-press-release**.
- «напиши резюме / CV / сопроводительное» → **write-resume**.
- «проверь / оцени текст, насколько живой» → **audit-text** (детектор AI).
- «проверь / оцени документацию» → **audit-docs** (редакторское качество и факты, шкала 1–10).
- «перепиши / оживи / убери AI» → **rewrite-text**.
- «настрой / определи мой стиль», «пиши как я» → **style-profile** (интервью и разбор образцов → локальный `style-profile.local.md`).

Граница audit ↔ rewrite: «оцени, что не так», это audit (диагноз, балл). «Сделай лучше», это rewrite (новый текст). Если из запроса неясно, спроси, что нужно: разбор или переписать.

Граница audit-text ↔ audit-docs: разная цель. **audit-text** ловит признаки AI (предсказуемость, ритм) в живом тексте. **audit-docs** оценивает редакторское качество и фактическую точность документации и не штрафует за нейтральный безличный тон, который для доков норма.

**Порядок генерации живого текста.** Скиллы write-post, write-article, write-readme, write-docs работают в обязательных фазах: (1) прочитать `style-profile.local.md`, если есть; (2) собрать фактуру, задать конкретные вопросы и не писать текст до ответов; (3) генерировать по правилам формата. Если `style-profile.local.md` нет, а пользователь просит написать живой текст, предложи сначала запустить **style-profile**.

Схема «сначала факты и голос от автора → генерация → правка», не вкус, а то, что подтверждает эмпирика. Причинное исследование AI-ассистированного письма (ACM LAK 2025, 1445 сессий) показало: правка AI-текста повышает качество, а принятие как есть снижает по всем метрикам. Авторы хотят AI как редактора, который флагует проблемы, а не переписывает целиком, отсюда и разделение **audit** (диагноз без переписывания) и **rewrite**.

Скиллы генерации **до текста читают `postroenie.md` и `mosty.md`**, потом применяют свои форматные правила; готовый черновик сверяют со словарём `writing-rules.md` и линтером. `audit-text` и `audit-docs` работают по словарю, `rewrite-text` разбирает исходник по словарю, а новый текст строит по `postroenie.md`. `mosty.md` override регистра (write-docs, write-vacancy, write-press-release, write-resume) не касается: честность связи между утверждениями обязательна в любом жанре. `audit-text`, `audit-docs` и `rewrite-text` дополнительно подтягивают форматный скилл под тип текста: пост → write-post, статья → write-article, README → write-readme, документация → write-docs.

**Локальный авторский голос.** Поверх ядра и формата работает третий, необязательный слой, `style-profile.local.md` в корне. Если файл есть, скиллы живого текста (write-post, write-article, write-readme, rewrite-text) пишут в голосе автора, описанном там. Хук в `postroenie.md` (раздел «Голос»), порядок слоёв: `postroenie.md` задаёт, как строится мысль → формат задаёт структуру → профиль задаёт голос; при конфликте по существу выигрывает `postroenie.md`. Собирает профиль скилл **style-profile**. Готовые профили-архетипы лежат в `voices/` (коммитируются, в отличие от локального `*.local.md`): можно взять любой за основу и скопировать в `style-profile.local.md`, потом подогнать. Файл локальный (`*.local.md` в `.gitignore`), у каждого автора свой, в гит не идёт. На документацию слой не распространяется, там нейтральный регистр.

**Реплики агента, отдельный слой, не скилл.** `chat-style.md` в корне, карточки ситуаций для обычных реплик Claude Code в диалоге: короткий ответ на короткий вопрос, детали по запросу, метка после смысла. Не скилл: у «отвечай всегда так» нет триггерной фразы, поэтому карточки и личные образцы из `style-profile.local.md` кладёт в контекст SessionStart-хук `scripts/chat_context.sh`, один раз на сессию (на каждый запрос дорого, текст копится в истории). Подключение хука личное и в гит не входит.

**Генерация отдельно от проверки.** Так устроены все скиллы генерации и `chat-style.md`: в контексте генерации то, как строить текст (`postroenie.md`, карточки ситуаций в скилле), а запреты читаются после черновика (`writing-rules.md`, `check.md` рядом со скиллом, `scripts/lint_text.py`). Причина в том, что список запретов в контексте генерации тянет модель к тем же штампам и не говорит, что писать вместо. Полностью по ситуациям пока переписаны `chat-style.md`, `write-message`, `write-post` и `write-article`, остальные скиллы держат старую структуру фаз поверх нового ядра. `scripts/stoplist.txt` это машинная выжимка лексических разделов словаря: правишь лексику в `writing-rules.md`, сверь и её.

**Документация, особый регистр.** write-docs содержит блок override: часть правил ядра в доках инвертирована (нейтральный тон вместо позиции, обязательный вывод вместо открытого финала, не начинать с союзов, числа до десяти словами). Любой скилл, работающий с докой, применяет ядро **после** этого override, а не вместо. Продуктовая специфика (термины, разметка, имена файлов меню) в TextSkill не живёт, она остаётся в локальной редполитике конкретного репозитория, write-docs только ссылается на неё.

## Чего пока нет

Осталось непокрытым: генератор под **описание товара для маркетплейса** (Ozon/WB). Жанр упирается в SEO-лимиты площадок, которые часто меняются, поэтому его стоит делать с конфигом лимитов, а не хардкодом. `audit`/`rewrite` этот тип знают, но профильного генератора пока нет. SEO-статья, не отдельный скилл, а режим write-article; newsletter, под-формат write-email.

Документация покрыта: **write-docs** (генерация) и **audit-docs** (аудит). Продающие и HR-жанры покрыты: **write-landing**, **write-kp**, **write-email** (живой голос), **write-vacancy**, **write-press-release**, **write-resume** (override-регистр). Но все они держат только жанр; продуктовая редполитика конкретного репозитория, отдельный локальный файл, который их дополняет.

## Дисциплина правок

- **Не раздувай списки.** Стоп-листы уже покрывают основные каталоги AI-маркеров (англо-Википедия «Signs of AI writing», инфостиль, авторский синтез; отдельной русской вики-страницы такого авторитета нет). Ещё одна строка почти не двигает качество, но грузит контекст. Лучше править формулировки в ядре, чем добавлять пункты.
- **Держи примеры краткими.** В скиллах с примерами (write-post, audit-text, rewrite-text) образец якорит планку, но один и компактный.
- **Синхронизация не нужна:** раз паттерны в одном месте, дублей нет. Если заметил копию стоп-листа где-то ещё, это баг, убери.

## Допущение путей

Скиллы читают `postroenie.md`, `writing-rules.md`, `mosty.md`, `audit.md` и `scripts/lint_text.py` со `scripts/stoplist.txt` из корня проекта через `${CLAUDE_SKILL_DIR}/../../../`. Копируешь скиллы в другой репозиторий, тащи эти файлы вместе с ними, иначе скиллы сломаются.
